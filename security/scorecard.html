Responsible disclosure · authorized hackathon testing

If you build it exactly the way the quickstart shows, is the token safe?

AssemblyAI's own Voice Agent starter puts a browser token in a client-visible WebSocket URL, and calls it “single-use” to justify that. We tested the claim on production. It doesn't hold — three ways.

Target: production real-time APIs Date: 2026-10-20 Scope: our own hackathon key only Repros: security/probes/
5/5SESSIONS, ONE TOKEN

One minted browser token opened five Voice Agent sessions at once, kept working on reuse for its full 600-second life, and drove paid TTS, STT and the Voice Agent interchangeably. The one-time promise is the basis for exposing it in a URL.

What the starter says

“a short-lived, single-use token minted here — so your API key never reaches the client.”
“The browser connects straight to the Voice Agent API with a one-time token.”
assembly init voice-agent → api/index.py, static/index.html, README.md

What production does

  • Reused across sequential opens — never spent.
  • 5 concurrent sessions from one token.
  • A streaming token also drives TTS and the Voice Agent, and vice-versa.
  • No per-token connection or spend cap.

Findings

High · A“Single-use” tokens are reusable and multi-session›
Impact

A token scraped from a URL, a log line, or a shared link keeps working for its whole 600s life — not the one shot the docs promise. Every app built from the official starter inherits this.

Fix

Bind a jti and burn it on the first session.ready. If multi-use is intended, stop calling it “single-use” and offer max_sessions=1.

High · BTokens aren't scoped to the product they were minted for›
Impact

A transcription widget that only needs speech-to-text hands out, in its page, a credential that also synthesizes speech and runs full $4.50/hr voice-agent sessions. Least privilege is violated by default.

Fix

Stamp an aud/scope claim into the token at mint time and enforce it at each service's handshake. Highest-leverage fix — it also contains finding A's blast radius.

Medium · CNo per-token cap → a leak is a cost-amplification vector›
Impact

Pricing is public. One scraped 600s token authorizes up to ten minutes of concurrent paid sessions across STT + TTS + Voice Agent + LLM, per use, billed to the account owner. Harvested at scale from a popular starter-based app, that adds up.

Fix

Cap concurrent sessions per token (ideally 1) and expose per-key spend/rate limits.

Fair · ✓What's already done right›

TTL is enforced and capped at 600s — a 3s token was rejected after 8s; 1-day and 1-year requests are refused with 422 ≤ 600. This bounds every finding above to a ten-minute window.

Errors don't leak. Malformed JSON, bogus fields, path-like voice names and bad keys all return terse, non-reflective errors — no internal hosts, file paths, or stack traces.
